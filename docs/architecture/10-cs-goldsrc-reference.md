# 10 GoldSrc / CS 参考（网络与预测域）

> 本篇编号 10（承 09 号文 §3 的清单委托；由 CS 1.5 逆向对比线草案经主会话 2026-11-08 定号入仓）。

参考对象：原版 Counter-Strike 1.5（2002-06-12，GoldSrc/Half-Life
mod 形态）与开源逆向实现 `github.com/FWGS/cs16-client`（CS 1.6，
Xash3D FWGS 生态）。2026-11-08 用户定案 slaengine 终极目标支持
三款游戏——魔兽第一、**CS 第二（正式支持目标）**、红警第三——
本篇即 CS 域的参考总纲。证据基：CS 1.5 原版素材静态测绘
（`~/workspace/cs15-re/RESULT.md`，下称「测绘」；素材全量哈希在
其 MANIFEST）+ cs16-client 仓树实查（HEAD `8ae1ebe2`）。

## 10.0 使用纪律（红线，先于正文）

1. **三参考中的第三参考，辖域限定**：本篇与魔兽域的双参考
   （原版阶段二逆向、OpenRealm）并列，但只辖**网络与预测域**
   （外加模块托管一域，见 §10.3）。CS 的玩法/数值/内容不构成
   slaengine 的规格来源；魔兽域事项仍以 04/05 为准，本篇不
   越界。
2. **行为参考，不取代码**：原版 CS 1.5 是商业游戏二进制，只做
   静态测绘（文件/符号/字符串/数据文件），其素材不入本仓、不
   外传；cs16-client 许可为 GPLv2+ 文本与 Half-Life SDK 血统
   混合（仓整体被标 NOASSERTION），纪律从严——学其组织与
   行为，**不搬其代码进引擎**，引用止于文件名/接口名/符号名。
3. **证据分层照实登记**：原版服务端二进制未 strip，符号级
   证据为真值级；原版客户端 DLL 整体加密（测绘 §1.3），客户
   端域的组织证据取自 cs16-client 重构源码，属行为级而非
   原版真值级，引用时逐处标明。
4. **支持目标 ≠ 复刻目标**：CS 列为正式支持目标，指 slaengine
   须具备托管 GoldSrc 类游戏的引擎面（§10.3 清单），不指逐位
   复刻 CS——玩法实现仍是届时立项的游戏侧工作，本篇只钉
   引擎面。

## 10.1 范式总览：GoldSrc 的联网模型

GoldSrc 的联网是**服务端权威 + 客户端预测-对账**制，与魔兽的
lockstep 制构成两种基本范式（05 §5.6 的 G6 为 lockstep 口径）：

| 维度 | GoldSrc / CS（本篇） | 魔兽 lockstep（05 G6） |
|---|---|---|
| 真值源 | 服务端单点权威 | 全体客户端模拟一致 |
| 同步物 | 实体状态快照的字段级差分 | 玩家命令流 + 校验和 |
| 客户端角色 | 先行预测本地玩家，候权威纠正 | 与全场同节拍推进模拟 |
| 确定性要求 | 不要求逐位一致（浮点容忍，对账兜底） | 逐位确定（定点、RNG 同步点钉死） |
| 带宽形态 | 随实体数与变化率增长 | 随玩家数与命令率增长，与单位数无关 |
| 录像 | 状态流录像 | 输入流回放 |
| 适配形态 | 小规模、高操作密度、即时判定 | 大规模单位、状态量爆炸 |

判读：范式由游戏形态决定，不是优劣问题。slaengine 三款游戏
全支持 ⇒ **双范式必须在同一引擎内共存**，共存设计见 §10.3-D。

## 10.2 机制参考（四域）

### 10.2.1 客户端预测与服务端对账

移动物理只有一份实现（pm_shared）：客户端用它先行推演本地
玩家的移动并即时呈现，同一份输入（usercmd）发往服务端以同
一份代码在权威世界重演；权威状态回传后，客户端对齐本地状
态——小误差平滑纠正（回到权威位后重放未确认输入），大误差
直接吸附。武器开火表现同理由客户端预测、服务端定命中真值。

- 证据：原版 cs_i386.so 符号表含 PM_* 函数族 40+ 个（PM_Move、
  PM_Friction、PM_Accelerate、PM_AirMove、PM_Duck、PM_Jump、
  PM_LadderMove 等），编进服务端 DLL；cs16-client 侧
  `pm_shared/pm_shared.cpp` 单份实现 + `cl_dll/hl/hl_weapons.cpp`、
  `cl_dll/com_weapons.cpp` 客户端武器预测（测绘 §2.1/§3.1）。
- 取法：**采纳组织原则**——模拟代码单一实现、多宿主复用，
  与物理座 `step(world, dt, inputs)` 签名纪律同向，升格为
  联网模拟通用纪律。**不采纳其实现形态**——GoldSrc 靠全局
  状态 + 引擎回调表共享移动上下文，slaengine 以纯函数式
  step + 显式状态快照实现同一原则（ECS 核心不容全局态）。

### 10.2.2 网络面：delta 压缩、状态同步、插值/外推

服务端以固定节拍生成实体状态快照，只发与上一确认快照的
字段级差分。差分规格是**数据文件**：每字段钉死位段类型、
位宽与量化除数（坐标 21 bit/÷128、速度 16 bit/÷8 一类），浮
点以定点化传输；游戏模块可挂条件编码例程在发送前裁剪字段。
客户端维护实体状态历史：他人实体以约 100ms 前的两帧状态
插值呈现，状态过期时短时外推；输入以冗余打包发最近数帧，
丢一包不丢输入。

- 证据：原版 `cstrike/delta.lst`（5 个结构、213 条字段定义；
  entity_state_t 与 entity_state_player_t 各挂 gamedll 条件
  编码例程 Entity_Encode / Player_Encode）；cs_i386.so 符号
  Entity_Encode、Player_Encode、Custom_Encode、RegisterEncoders
  与之逐一对应（测绘 §1.5/§3.2）。
- 取法：**delta 规格数据化采纳**——slaengine 的同步字段以声明
  表给出（位宽、量化、更新条件），引擎只做通用编解码；此形
  与 SAB 注册表联邦化（包自带表面清单）同型，可互相借力。
  **插值缓冲与外推兜底采纳为客户端呈现层标准件**（魔兽域的
  单位呈现平滑同样需要）。1.5 的具体量化数值不采纳（其地图
  尺度与带宽年代的产物，按自家尺度重定）。

### 10.2.3 引擎↔游戏模块边界

引擎与游戏模块的全部关系收敛在三处：描述文件声明模块路径
与宿主版本；装载时一次握手——引擎交付引擎函数表、模块回
交游戏函数表，版本不合即拒载；此后双方只经函数表互调。游
戏模块运行时零直接系统依赖（服务端 DLL 仅导入 KERNEL32 /
仅依赖 libm、libc），不碰套接字与文件系统。实体扩展在原版
靠「引擎按 classname 查 DLL 导出表同名工厂函数」的约定。

- 证据：原版 `cstrike/liblist.gam`（gamedll/gamedll_linux/
  cldll/hlversion 字段）；mp.dll 356 个导出（握手面 + 实体
  类名导出群）；cs16-client `engine/eiface.h` 的 enginefuncs_s
  约 217 处函数指针声明（引擎回调面宽度实测）、
  `engine/APIProxy.h`（换引擎而模块契约不变的开源实证）
  （测绘 §1.2/§3.3）。
- 取法：**握手 + 版本门 + 模块零系统依赖采纳**（描述符声明、
  装载期双向表交换、版本不合响亮拒载，与本引擎「描述符注册
  表、函数指针顶替宏」的轻机制同路）。**按名查导出表的实体
  工厂明确不采纳**——无静态检查、运行时才炸，本引擎的描述
  符注册表路线严格优于它。引擎回调面 217 的宽度作**警示性
  参照**：slaengine 的域/座接口须保持窄面、按域分组。

### 10.2.4 确定性面

GoldSrc 只有服务端是真值源：RNG、命中、经济都在服务端单点
决定；双端同源的移动代码不保证跨机逐位一致，协议以对账兜
底，设计上放弃模拟确定性，换取实现自由与即时手感。其录像
记状态流、不依赖重演。此范式与魔兽的取舍对照见 §10.1 表；
对 slaengine 的硬含义是：**确定性纪律不是全引擎一刀切**——
lockstep 辖域内定点刚需不变（01 §1.3 确定性条），权威环辖域
内允许浮点预测，但同一物理实现被两环共享时以定点版为准入
线（冲突点全表见 §10.3-D）。

## 10.3 支持 CS 所需引擎面清单

CS 为正式支持目标（第二顺位），故本篇除参考分析外钉一份引擎
面清单：slaengine 若要托管 GoldSrc 类游戏，下列面必须成立。
每项给证据出处与难度/风险；难度按「在现有架构上新增的工程
量」估，风险按「与既定定案（魔兽第一、ECS 核心、定点纪律）
的冲突度」估。

### A. 模块托管面

| 引擎面 | 内容 | 证据出处 | 难度 | 风险 |
|---|---|---|---|---|
| A1 游戏描述符 | 一份声明钉死：游戏模块路径（分平台）、宿主版本要求、单机/联机类型、安全/认证标志；引擎据此装载与拒载 | 原版 liblist.gam 全字段（测绘 §1.1） | 低 | 低：与既有描述符注册表同路 |
| A2 装载握手与版本门 | 引擎交引擎面、模块交游戏面，一次交换双向函数/接口表；版本不合响亮拒载，不降级运行 | 原版 GiveFnptrsToDll / GetEntityAPI(2) / GetNewDLLFunctions（测绘 §1.2） | 低 | 低 |
| A3 双模块分置 | 同一游戏含服务端模块与客户端模块两件，接口面不同、生命周期不同（服务端随对局、客户端随会话）；单机 = 内嵌服务端与客户端同进程对接 | 原版 dlls/ 与 cl_dlls/ 分置 + cldll 标志；魔兽侧 OpenRealm 的内嵌 server 形态同型（04 §4.1） | 中 | 中：与魔兽导入族（N1）的模块观须统一成一套托管协议，不许两游戏两套 |
| A4 实体/组件注册面 | 游戏模块把实体类（工厂 + 同步字段表 + 规则挂点）登记进引擎；走编译期描述符注册，拒绝 GoldSrc 的「按名查导出表」运行时约定 | 原版 356 导出的类名群（反面教材）；cs16-client dlls/ 头文件群（类声明面） | 中 | 低：本引擎既定路线即注册表 |
| A5 生命周期事件面 | 引擎向模块派发：初始化、关卡载入/切换、对局开始/结束、玩家连接/断开、帧步进；模块不得自起线程绕过引擎节拍 | 原版 DLL_FUNCTIONS 表的事件构成（cs_i386.so 符号面）；changelog 中 changelevel 相关条目 | 中 | 中：帧步进事件与 ECS 调度、lockstep 回合节拍的编排关系须先定（与 D2 联动） |
| A6 模块沙箱纪律 | 游戏模块零直接系统依赖：不碰套接字/文件/时钟，一切经引擎面；便于双范式托管与回放 | 原版 mp.dll 仅 KERNEL32、cs_i386.so 仅 libm/libc（测绘 §1.2） | 低 | 低 |

### B. 预测-对账联网环（与 05 的 G5/G6 并列的第二条环）

| 引擎面 | 内容 | 证据出处 | 难度 | 风险 |
|---|---|---|---|---|
| B1 服务端权威模拟环 | 服务端按固定节拍推进权威模拟，单点决定 RNG/命中/经济；客户端模拟结果永不回写真值 | 测绘 §3.1/§3.4（服务端类普查 + 符号面） | 中 | 中：与 ECS 模拟核心共用时，权威环的「服务端独占真值」与 lockstep 的「全端同算」是两种世界状态所有权，须在世界抽象层分型 |
| B2 客户端预测执行器 | 客户端以同一份模拟代码先行推演本地玩家；需要：输入采样与编号、未确认输入队列、权威对齐后的按序重放 | pm_shared 双端同源 + usercmd_t 契约（测绘 §1.5/§3.1）；cs16-client pm_shared/ 与 cl_dll 预测面 | 高 | 高：预测执行器要求模拟步进可任意重演（纯函数 + 快照可回滚），与 ECS 并行调度的张力是本清单最大单点（与 D1 联动） |
| B3 快照-delta 同步面 | 字段级差分同步：同步字段声明表（位宽/量化/更新条件回调）、基线快照确认与重同步、条件编码挂点 | delta.lst 213 条定义 + Entity_Encode/Player_Encode 符号对位（测绘 §1.5） | 中 | 低：与 SAB 注册表联邦化同型，可共设计 |
| B4 呈现平滑面 | 他人实体插值缓冲（约 100ms 历史窗）、状态过期外推、本地预测与远端呈现的双轨呈现 | 测绘 §3.2；cs16-client common/net_api.h、cl_dll/entity.cpp | 中 | 低：纯客户端呈现层，不碰模拟真值 |
| B5 输入冗余与节拍解耦 | 输入包冗余携带最近数帧命令；渲染节拍、预测节拍、网络节拍三者解耦 | usercmd_t 的 delta 定义面（测绘 §1.5） | 低 | 低 |
| B6 延迟补偿（服务端回溯） | 服务端处理命中判定时按射手视角时刻回溯目标位置——权威环的标准件，缺之则手感与公平性俱损 | 范式固有需求；本轮测绘未取到仓内直接证据，**证据层级：待专项核**（候 Xash3D 引擎侧与 cs16-client 专项核查） | 中 | 中：回溯要求服务端保留实体历史环，与 B2 的快照纪律同源设计 |

### D. 与魔兽 lockstep 同步面的共存关系与冲突点

| # | 议题 | 关系/冲突内容 | 处置建议 |
|---|---|---|---|
| D1 | 模拟确定性 | lockstep 环要求模拟逐位确定（定点）；权威环容忍浮点、以对账兜底。冲突在共享层：物理/移动代码若两环共用，浮点版会污染 lockstep 的确定性 | 物理实现以定点版为两环共同准入线；浮点只许活在权威环的预测/呈现侧，不得进入任何被 lockstep 消费的步进路径 |
| D2 | 时钟与节拍 | lockstep 是全场统一回合节拍（输入延迟换同步）；权威环是服务端快照节拍 + 客户端自由渲染节拍。同引擎帧循环内两套时钟并存 | 帧循环按「环」编排：每游戏实例选定一环，引擎只提供节拍源抽象（回合节拍源 / 快照节拍源），不许两环混跑于同一对局 |
| D3 | 世界状态所有权 | lockstep：状态在全端复制、命令是唯一输入；权威环：状态只在服务端、客户端持预测副本 | ECS 世界抽象须分型：复制型世界（replicated）与权威型世界（authoritative + predicted shadow），两型的系统调度与快照接口分别成面 |
| D4 | 录像/回放 | lockstep 录输入流即可重演；权威环必须录状态流（或服务端全量日志） | 录像格式双轨并存、文件头标明范式；回放器按范式分发，不做统一重演假设 |
| D5 | 作弊面与信任模型 | lockstep 客户端被信任持有全量状态（信息隐藏弱）；权威环客户端只见服务端下发状态（可做信息裁剪），但预测面扩大了输入伪造面 | 信任模型不跨环继承：权威环须有服务端输入校验与状态裁剪面；lockstep 环的信息暴露按魔兽域既有口径处理 |
| D6 | 共享下层 | 传输层（连接、可靠/不可靠通道、包分片）、资产层、渲染呈现层与两环无关 | 明确共享：传输与资产只做一次；同步语义（B 环与 G5/G6）在模拟步进处分家，不许在传输层掺同步策略 |

## 10.4 登记事项（未决与待核）

1. **引擎侧证据缺口**：本篇的引擎面证据取自游戏模块侧与开源
   接口头；GoldSrc 引擎本体的托管实现（Xash3D FWGS 引擎仓）
   未在本轮测绘内。若 CS 支持进入实现期，Xash3D 引擎仓应列
   为托管面的行为参考（同纪律：学组织与行为，不取代码）。
